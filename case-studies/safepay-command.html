SafePay Command: AI payment-risk platform

Scams where the customer sends the money look like normal payments, so a risk model alone cannot see them. This platform asks a few questions, lets versioned rules decide, and records every step so it can be checked.

TypePersonal project
DomainFintech, payment risk
FocusEvaluation, safety, auditability
LinksLive demo · Code

The problem

Stopping too many payments annoys good customers, and missing scams loses money. In authorised-push scams the payment is made by the real customer, so only the customer's story reveals the problem. Sanctions screening has the same trade-off between missed matches and false alerts.

What I built

  • A LightGBM risk model trained on a real public card-payment dataset, with time-ordered splits and calibrated bands.
  • A question step: up to three customer questions when a payment looks risky, with warning signs read from the answers. Flags can only add friction.
  • Versioned rules (policy as data) that decide allow, warn, hold or block. The LLM never makes the final decision.
  • An LLM gateway with PII redaction, injection screening, Pydantic schema validation, sentence-level fact-checking, fallbacks and a daily cost cap.
  • Fuzzy sanctions-list name screening (OFAC) and an analyst case workflow with recorded overrides.
  • A tamper-evident hash-chained audit ledger that the browser can verify.
  • Accounts, roles and rate limits; deployed on Vercel, Railway and Neon; 320 automated tests including PostgreSQL race-condition tests.

Results

  • Risk model: average precision 0.812 on a time-ordered test set with 75 frauds (95% interval 0.727 to 0.894). At an alert level that lets 1% of good payments alert, recall is 88% and precision 14%.
  • Simulated scams: rules alone, and rules plus the model, caught 0 of 80 by design. Adding questions caught about half to two thirds. Pooled over two test sets, AI-written questions held 57% and fixed questions 50% (p = 0.052), and the two catch different scams. Coached victims are mostly missed.
  • What did not help: graph features added +0.000 average precision, and a model trained before a market shutdown fell from 0.912 to 0.048 afterwards.

Design decisions

  • The LLM never decides. It asks, explains and summarises; rules decide.
  • Every AI step has a plain fallback, so the flow works when the model is slow or wrong.
  • Report what did not work. Negative and inconclusive results are published with the rest.

What I would improve

  • Replace simulated customers with real, consented conversations in a small pilot.
  • Add production monitoring for drift, alert rates and AI fallback rates.
  • Improve name redaction and move rate limiting to a shared store.
