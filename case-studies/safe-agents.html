Making AI agents safe to run on live stores

Verify-before-report flows, structured human-in-the-loop questions and approval gates for agents that change live e-commerce stores.

RoleApplied AI Engineer
DomainE-commerce, live stores
FocusAgent reliability and safety
Client namesNot shown

The problem

A demo agent can be wrong and nobody gets hurt. A production agent that edits a storefront, publishes content or changes what shoppers see cannot afford that. The most common failure was not a bad answer. It was an agent saying a task was complete when it was not: a save worked, the generated output was empty, and nothing reached the page.

Goal: agents that change live systems, with no silent failures and a person in control of anything risky.

Constraints

  • The agents act on live storefronts, so a wrong action is visible to real shoppers.
  • Several agents (experiments, SEO, publishing) share one platform and must behave consistently.
  • Model gateways reject schemas they do not fully support, so tool definitions must stay simple.

Design decisions

1. Verify before reporting

Every flow that changes something live follows the same order, and any failed step is reported honestly instead of skipped.

Save→Generate→Check output→Apply→Report
Check fails→Stop and report the failure

2. Structured human-in-the-loop questions

When the agent is unsure, it asks, it does not guess. The question has a clear prompt, a small set of options and a response ID, so the answer maps back to the exact question. This is easier to render in a UI, easier to audit and harder to misread than free text.

3. Approval before going live

For bigger changes, such as an experiment across many products, the agent builds previews first. A person reviews them and approves. Only then does anything go live. One small gate removes a whole class of "the agent changed the wrong thing" incidents.

Build previews→Person reviews→Approve→Go live

4. Boring tool schemas

Strict model gateways rejected clever schema types. Plain arrays and simple objects work everywhere, so I keep tool schemas boring and JSON Schema compatible.

A failure that taught a lesson

One agent used browser automation to edit page elements and built selectors from an element's id. On some pages a form contained a child input named "id", and reading the property returned that input instead of the string. The selector became an object string and the agent retried again and again.

Fix: read the attribute directly, validate it as a safe identifier, and fall back to a structural path otherwise. Lesson: agents amplify small bugs because they retry, so put limits on retries and make failures loud.

What I would improve

  • Turn every production failure into an automated eval case that runs before each release.
  • Add per-step tracing dashboards so the cost and latency of each tool call are visible.
  • Re-check live state right before a write, and re-ask for approval if it changed since approval.
